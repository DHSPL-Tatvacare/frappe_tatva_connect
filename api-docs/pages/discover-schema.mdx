Call `lead_schema` to find out what your key can send and read. It returns the lead fields, which of them are required, the sections, and how your key sets the program.

:::note{title="Read the schema, don't hardcode it"}

Each key has its own schema. It changes when TatvaCare changes your key's access. Call `lead_schema` when your integration starts, and build your requests from the response. Don't copy a field list from this page.

:::

```bash title="Request"
curl "$BASE_URL/api/method/tatva_connect.api.partner.lead_schema" \
  -H 'Authorization: token <api_key>:<api_secret>'
```

## What each part means

| Part | What it tells you |
|---|---|
| `entity` | What the schema describes. Here, `lead`. |
| `identity` | How you address a record. `addressed_by` is always `name`. |
| `fields` | The lead fields your key can use. See [Field attributes](#field-attributes). |
| `children` | The sections your key can use, keyed by name, for example `custom_lab_profile`. |
| `children.<section>.multi_row` | `true` if the section holds many rows. `false` if it holds one. |
| `children.<section>.key_field` | For a section with many rows, the field that identifies each row. `null` for a section with one row, and for form answers. |
| `children.<section>.fields` | The fields in that section, described the same way as `fields`. The `key_field` is always listed, and marked required, because you send it with every row. |
| `dedup` | How the CRM decides that two leads are the same, as text. |
| `child_write` | How to write sections, as text. |
| `bulk.max_per_call` | The most records one bulk call accepts. |
| `bulk.payload_key` | The JSON key each bulk call reads its array from. A bulk body under the wrong key is refused. |
| `bulk.list_page_max`, `bulk.list_page_default` | The largest and the default page size for `lead_list`. |
| `list_filters` | The filters `lead_list` accepts. |
| `routing` | How your key sets the product line, group, and program. See [Routing](#routing). |

### Field attributes

Each entry in `fields`, and in a section's `fields`, describes one field:

| Attribute | What it tells you |
|---|---|
| `fieldname` | The JSON key, for example `mobile_no`. |
| `label` | The display name, for example `Mobile No`. |
| `type` | The data type, such as `Data`, `Int`, `Float`, `Date`, `Link`, or `Select`. |
| `behavior` | `REQUIRED`, `OPTIONAL`, or `OUTPUT_ONLY`. You can read an `OUTPUT_ONLY` field, but you can't set it. |
| `required` | `true` if you must send the field when you create a lead. |
| `options` | For a `Select` field, its values. For a `Link` field, the name of the list its values come from. `null` for other types. |

Two more attributes appear only on the fields they apply to:

| Attribute | What it tells you |
|---|---|
| `allowed_values` | The exact values your key can send for this field. When it's present, use it instead of `options`. |

For a `Link` field without `allowed_values`, send a value from the list that `options` names. If the value isn't in that list, the API returns `400 validation_error`.
| `multi` | `true` if the field takes a JSON array of values instead of one value. |

Read attributes by name, not by position. If an attribute is missing, it doesn't apply to that field. New attributes may be added later, and they won't break your client.

Two attributes affect every write.

If you send a value for an `OUTPUT_ONLY` field, the API ignores it and still returns `200`. So a `200` doesn't prove that such a field was saved.

The API checks each value against its `type`. If a value doesn't fit, the API returns `400` and names the field. Send numbers as numbers, and dates in ISO format, such as `2026-05-18`.

## Sections

Send each section as a JSON array inside the lead body. There are three kinds of section: many rows, one row, and [form answers](#form-answers). `multi_row` and `key_field` tell you which one you have.

To list the sections your key can use, and what kind each one is, pipe `lead_schema` through [jq](https://jqlang.org):

```bash title="Request"
curl -s "$BASE_URL/api/method/tatva_connect.api.partner.lead_schema" \
  -H 'Authorization: token <api_key>:<api_secret>' \
  | jq -r '.data.children | to_entries[] | "\(.key)\t\(if .value.multi_row and .value.key_field == null then "form answers" elif .value.multi_row then "many rows, key: \(.value.key_field)" else "one row" end)"'
```

For the example response above, this prints:

```text title="Output"
custom_lab_profile	many rows, key: report_date
custom_screening_answers	form answers
custom_care_providers_profile	one row
```

To list the fields in one section, use its name in the path:

```bash title="Request"
curl -s "$BASE_URL/api/method/tatva_connect.api.partner.lead_schema" \
  -H 'Authorization: token <api_key>:<api_secret>' \
  | jq -r '.data.children.custom_lab_profile.fields[].fieldname'
```

```text title="Output"
hba1c
report_date
```

### Sections with many rows

Each row is identified by the section's `key_field`. For the lab section, that's `report_date`. When you send rows:

- A new key value adds a row.
- An existing key value updates that row. Only the fields you send change.
- Rows you don't send stay as they are.
- To delete a row, use the `_delete` keyword. See [Deleting a row](#deleting-a-row).

Always send the `key_field`. If you leave it out, the CRM still adds the row, and sets its key to the date or time the row arrived. To change that row later, you must send that same value.

### Deleting a row

To remove a row, send an object with the row's `key_field` value and `"_delete": true`:

```json title="Request body"
{
  "mobile_no": "+919900000000",
  "custom_lab_profile": [
    { "report_date": "2026-01-10", "_delete": true }
  ]
}
```

`_delete` isn't a field. It's a [keyword](/keywords) that tells the CRM to remove the row with that key.

- It works only in sections with many rows. In a section with one row, the API ignores it.
- The object must include the row's key. Without it, the API returns `400 validation_error`, because it can't tell which row to remove.
- If no row has that key, nothing changes.

### Several changes in one write

You can add, update, and delete rows in the same request. This body updates the `hba1c` of the 2026-05-18 row, adds a row for 2026-06-20, and deletes the 2026-01-10 row. It leaves all other rows as they are.

```json title="Request body"
{
  "mobile_no": "+919900000000",
  "custom_lab_profile": [
    { "report_date": "2026-05-18", "hba1c": 6.9 },
    { "report_date": "2026-06-20", "hba1c": 6.4 },
    { "report_date": "2026-01-10", "_delete": true }
  ]
}
```

### Sections with one row

Send an array with one object. The CRM merges its fields onto the lead's single row. If the lead doesn't have that row yet, the CRM creates it. If you send more than one object, the API returns `400 validation_error`.

```json title="Request body"
{
  "mobile_no": "+919900000000",
  "custom_care_providers_profile": [
    { "custom_doctor_name": "Dr Iyer" }
  ]
}
```

:::tip{title="Send only what you have"}

In both kinds of section, the CRM changes only the fields you send. The rest of the row, and every row you don't send, stays as it is. So you can send new details as they arrive.

:::

### Form answers

Use `custom_screening_answers` for answers from a lead form, such as a Facebook lead ad or a form on your website. Each answer is a question-and-answer pair, so you can send any question your form asks. You don't set questions up in advance.

Your key can send form answers only if TatvaCare has granted this section. `lead_schema` then lists `custom_screening_answers` under `children`, with `multi_row: true` and `key_field: null`.

Each answer is an object with three fields:

| Field | What it holds |
|---|---|
| `question` | Your own ID for the question, such as `condition_managing`. Required. Keep it the same for good, because the CRM uses it to match answers to the same question. |
| `label` | The question as the person saw it. You can change it at any time. |
| `value` | The answer. For a question with several choices, send a list. |

This body sends two answers. The second is a question with several choices:

```json title="Request body"
{
  "mobile_no": "+919900000000",
  "custom_screening_answers": [
    { "question": "condition_managing", "label": "Which condition are you managing?", "value": "Type 2 Diabetes" },
    { "question": "preferred_language", "label": "Which languages do you speak?", "value": ["Hindi", "English"] }
  ]
}
```

Send it with `lead_create` or `lead_update`, like any other section. The CRM saves answers this way:

- A question the lead hasn't answered adds an answer.
- A different answer to a question the lead has already answered is added too. The earlier answers are kept, so you have the history.
- The same answer again changes nothing. So you can safely send the whole form again.
- A list is saved as one answer, with the choices joined by a comma and a space, in the order you sent them.
- You can't delete an answer.

Send each question once per request. The API returns `400 validation_error` for a question sent twice, a row without `question`, or a `value` that holds an object or a nested list.

When you read the lead, each answer comes back with its own `name`, oldest first. The last answer to a question is its current one:

```json title="Response"
{
  "custom_screening_answers": [
    { "question": "condition_managing", "label": "Which condition are you managing?", "value": "Type 2 Diabetes", "name": "…" },
    { "question": "preferred_language", "label": "Which languages do you speak?", "value": "Hindi, English", "name": "…" },
    { "question": "condition_managing", "label": "Which condition are you managing?", "value": "Prediabetes", "name": "…" }
  ]
}
```

Here the person later changed their answer to `condition_managing`, so `Prediabetes` is the current answer.

## Routing

Your key sets the product line (`vertical`) and group of every lead. It also sets `source`, unless your key lets you send your own. You don't send the product line or group, and you can't move a lead to another one.

`routing.mode` tells you how to handle the program. [Programs](/concepts#programs) explains each mode.

## Reading rows back

When you read a lead with `lead_get` or `lead_get_bulk`, each section row includes two values you can use in your next write:

- `name`: the row's unique ID, for example `a1b2c3`.
- The row's `key_field`, such as `report_date`.
