This page explains how the CRM identifies a lead and what your key can reach. It also covers programs and sections.

## How the CRM identifies a lead

The CRM identifies a lead by three values together:

| Part | Field | What it is |
|---|---|---|
| Phone | `mobile_no` | The phone number in E.164 format: `+`, the country code, then the number, with no spaces or hyphens. For example, `+919900000000`. |
| Product line | `custom_vertical` | The product line of TatvaCare that the lead belongs to. |
| Group | `custom_group` | The group within that product line. |

Your key sets the product line and group. You send only the phone number.

If you send a phone number the CRM already has in your product line and group, the CRM updates that lead. It doesn't create a second one. The same phone number in a different product line or group is a different lead.

<Mermaid chart={`
flowchart LR
  P["mobile_no<br/>(you send)"] --> K{{"one lead"}}
  V["Product line<br/>(from your key)"] --> K
  G["Group<br/>(from your key)"] --> K
  K --> R["Send the same three again:<br/>the CRM updates this lead"]
`} />

Each lead also has a **unique ID** in the `name` field, for example `a7f3c9e12b`. Use it to read, update, or delete the lead.

## What your key can reach

Your key belongs to one product line and group. It can reach only the records in them. This applies to every endpoint, every method, and every bulk call.

If you ask for a record your key can't reach, the API returns `404 not_found`. It gives the same answer for a record that doesn't exist. This is on purpose, so don't try to tell the two apart.

Activities, calls, notes, and files belong to a lead. Your key can reach them only when it can reach their lead. The API checks this from the record's lead, not from anything you send. Sending a different ID won't reach a record outside your product line and group.

Tickets belong to a product line and group directly. Your key can reach a ticket, and its comments, when the ticket is in your product line and group.

You can delete only records you can read. The API won't delete a lead that has linked records, such as activities, calls, or notes. It returns `409 cannot_delete` instead, so the lead's history is kept.

## Programs

The program (`custom_current_program`) is the lead's current program. It isn't part of the lead's identity. If you change a lead's program, it stays the same lead.

Your key's mode decides how you handle the program. `lead_schema` reports the mode in `routing.mode`:

| Mode | What you do |
|---|---|
| `forced` | Don't send it. Your key sets it. If you do send it, the API ignores it. |
| `list` | Send one of the programs in `routing.allowed_programs`. If `routing.program_required` is `false`, you can leave it out, and the program is set later in the CRM. |
| `none` | Don't send it. Leads have no program. |

To move a lead to a new program, send the same phone number with the new program.

## Sections

A lead has sections for extra details, such as lab results, plan details, and the care team. Each section is a JSON array inside the lead.

<Mermaid chart={`
flowchart TD
  L["Lead"] --> PP["Plan section<br/>subscription, program, payment"]
  L --> LP["Lab section<br/>lab values, vitals, scores"]
  L --> CP["Care section<br/>coaches, doctor, hospital"]
`} />

A lead can have data in several sections at once. You never call a section on its own. Send it in the `lead_create` or `lead_update` body, and read it in the `lead_get` response. For example, the lab section is `"custom_lab_profile": [ ... ]`.

When you send a row, the CRM changes only the fields you send. It never clears the rest of the row. [Schema discovery](/discover-schema) explains how the CRM matches rows.

## Status

Every lead has a `status`, such as `New` or `Converted`. Read the values your key can send from [`lead_schema`](/discover-schema). Don't hardcode them. If your key can also set a finer stage, `lead_schema` lists that field too.
