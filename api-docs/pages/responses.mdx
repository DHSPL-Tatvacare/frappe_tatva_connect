---
title: Response shapes
---

Every call returns one of three top-level shapes.

## A single record

Returned by `lead_create`, `lead_update`, `lead_delete`, and `lead_get`:

```json
// HTTP 200
{
  "status": "success",
  "action": "created",
  "data": {
    "name": "a7f3c9e12b",
    "external_id": null,
    "first_name": "Example",
    "mobile_no": "+919900000000",
    "status": "New",
    "source": "…",
    "custom_vertical": "…",
    "custom_group": "…",
    "custom_current_program": "…",
    "custom_lab_profile": []
  }
}
```

- `status` is `"success"`.
- `action` is `created`, `updated`, or `deleted` for writes, or `fetched` for reads.
- `data` is the record itself. A write and a `lead_get` return the **same** projection — every field the key is granted, the routing under `source`, `custom_vertical`, `custom_group` and `custom_current_program`, and each granted child table as an array. `lead_schema` returns the schema here instead.

Because a write returns the stored record, a create or an update does not need a `lead_get` after it. On a delete, `data` carries only `{ "name": "…" }`.

:::note{title="Routing is named differently in the schema"}

On a record, the routing reads `custom_vertical`, `custom_group` and `custom_current_program` — the field names. Under `lead_schema.routing` the same three are reported as `vertical`, `group` and `program`, because that block describes the key rather than a lead. See [Schema discovery](/discover-schema#routing).

:::

## A list

`lead_list` returns a page object under `data`:

```json
// HTTP 200
{
  "status": "success",
  "action": "fetched",
  "data": { "total": 240, "count": 20, "offset": 0, "limit": 20, "leads": [ /* curated leads, no children */ ] }
}
```

`total` is the full count for the applied filters, and `leads[]` is the current page. Paging is by `offset`, up to 200 per page. Lists omit child tables; `lead_get` returns a full record.

## A bulk batch

Every bulk method returns HTTP 200 even when some rows fail. `summary` is read first, then `results[]` is walked:

```json
// HTTP 200
{
  "status": "success",
  "summary": { "total": 2, "succeeded": 1, "failed": 1 },
  "results": [
    { "index": 0, "status": "success", "action": "created", "data": { "name": "d41c8b7e05" } },
    { "index": 1, "status": "error", "error": { "code": "validation_error", "message": "mobile_no is required" } }
  ]
}
```

- `summary` is `{total, succeeded, failed}` for writes, or `{requested, found, not_found}` for `lead_get_bulk`.
- `results[]` is input-ordered, so `results[i]` is the outcome of the i-th item sent.
- A successful row carries its record under `data` — the address is `results[i].data.name`, never `results[i].name`.
- Each row carries its own `status`; a failed row carries the same `error` block as a single-call failure.

:::caution{title="A 200 does not mean every row landed"}

On bulk, each `results[].status` must be checked, not only the top-level one. One bad row reports its error while the rest still commit.

:::

## A failure

Any failure returns this shape, with a matching HTTP status:

```json
// HTTP 400
{ "status": "error", "error": { "code": "validation_error", "message": "…" } }
```

`error.code` is stable and is the value to branch on; `error.message` is human-readable. The full per-code table is on [Errors](/partner-errors), and [Reading values](/reading-values) covers reading any value by its path.
