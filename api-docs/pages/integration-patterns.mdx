This page shows how to build an integration that is correct, safe to retry, and light on your rate limits. The key difference to plan for: sending a lead again updates it, while sending any other record again creates a new one.

## Read the schema at startup

Your key decides which fields you can use. So read them from the API instead of hardcoding them.

<Stepper>

1. Call [`lead_schema`](/discover-schema) when your integration starts. A `200` also confirms your key works.

2. Build your field list from `fields`. Send every field whose `behavior` is `REQUIRED` on every create. Never send an `OUTPUT_ONLY` field.

3. Read `routing.mode`. It tells you whether to send the program. See [Programs](/concepts#programs).

4. Read `bulk.max_per_call`, `bulk.max_per_read` and `bulk.payload_key`. They give you the bulk write limit, the bulk read limit and the body key for each bulk call.

</Stepper>

Keep the schema in memory while your integration runs, and read it again when it restarts. It only changes when TatvaCare changes your key's access.

## Send leads without checking first

Many integrations read first, then create or update. For leads you don't need to. `lead_create` already creates the lead, or updates it if the phone number exists:

<Mermaid chart={`
flowchart LR
  A["Your lead"] --> B["lead_create"]
  B --> C{"action"}
  C -- created --> D["New lead:<br/>store data.name"]
  C -- updated --> E["Existing lead:<br/>fields updated"]
`} />

Sending the lead directly is better in three ways:

- You make one call instead of two.
- It stays correct when two requests arrive at once. With a read first, another request could create the same lead between your read and your write. `lead_create` handles that case.
- It uses half as many calls from your [rate limits](/rate-limits).

`action` in the response still tells you whether the lead was new.

A lead is the same lead across programs. If you send the same phone number with a new program, the CRM moves the existing lead to that program.

## When to read first

Read first only when you can't decide from your own data:

| Situation | Calls | Why |
|---|---|---|
| You must not overwrite what the CRM already holds | `lead_get`, compare, then send only the changes | A write saves every field you send. |
| You're checking a batch against the CRM | `lead_get_bulk` with `updated_after` | One paged read is cheaper than one read per lead. |
| You only need to know whether a lead exists | `lead_get` | `404` means it doesn't exist, or your key can't reach it. |

To leave a field unchanged, leave it out. An empty value (`""` or `null`) also counts as not sent, so you can't clear a field that way.

## Protect creates for everything else

Activities, calls, notes, files, tickets, and comments aren't checked for duplicates. Each create makes a new record. Do one of these for every record you create:

- Store the `name` the create returns, and send later changes as updates to that `name`.
- Send each create with an `Idempotency-Key` that stays the same for that record. Then a retry returns the first response instead of creating a second record.

A key made from your own record ID needs no extra storage, because every retry of that record carries the same key. For example, use a SHA-1 hash of `activity:` followed by your activity ID.

[Writes and retries](/writes-and-retries) explains both in full.

:::caution{title="A daily resync is safe for leads only"}

Resending yesterday's leads updates the same leads. Resending yesterday's activities, calls, notes, files, tickets, or comments creates duplicates. Send only new records, and update existing ones by their `name`.

:::

## Choose the right kind of call

| How many records | Use | Why |
|---|---|---|
| A few, and you need each result now | Single calls, such as `lead_create` | The result comes back in the same call. |
| Tens | Bulk calls, such as `lead_create_bulk` | Up to 25 records in one call, with one result per record. |
| Thousands, or a backfill | An [async bulk job](/async-bulk) | Runs in the background, with larger limits. |

Send bulk writes one after another. By default, a key can make one bulk write every 5 seconds, so parallel bulk writes return `429`.

## A typical flow

<Mermaid chart={`
flowchart TD
  S["Read lead_schema<br/>at startup"] --> L["lead_create<br/>for each changed lead"]
  L --> N["Store data.name<br/>with your own ID"]
  N --> A["activity_create<br/>with an Idempotency-Key"]
  A --> R{"429 or 503?"}
  R -- yes --> W["Wait retry_after,<br/>send the same call"]
  W --> A
  R -- no --> K["Check the result"]
`} />

Send only records that changed. The daily limits count records, so resending unchanged records uses them up.

To check each response, follow [Response shapes](/responses#read-every-response-the-same-way).

## Before you go live

- Your integration reads `lead_schema` at startup and hardcodes no fields.
- Phone numbers are in E.164 format, with the country code. See [Phone format](/conventions#phone-format).
- You store every `name` the API returns, next to your own record ID.
- Every create, except `lead_create`, carries a stable `Idempotency-Key`.
- On `429` and `503`, you wait `retry_after` seconds and retry, with a small random delay. See [Rate limits](/rate-limits).
- You send bulk writes one after another, not in parallel.
- You check `status` on every entry of a bulk response.
- You branch on `error.code`, never on the message text. See [Errors](/partner-errors).
- You tested everything on UAT first. See [Environments](/conventions#environments).
