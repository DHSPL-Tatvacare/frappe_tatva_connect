## 1. Get a key and set the base URL

TatvaCare issues your key for your integration. You get two values: an `api_key` and an `api_secret`. The secret is shown only once, so store it somewhere safe.

Send both in one header, joined by a colon:

```http title="Header"
Authorization: token <api_key>:<api_secret>
```

Use lowercase `token`, then one space, then `key:secret`. [Conventions](/conventions#authentication) has the exact format.

The examples use `$BASE_URL` for the host. Set it to the UAT environment while you build:

```bash title="Terminal"
export BASE_URL=https://one-uat.tatvacare.in
```

[Conventions](/conventions#environments) lists all environments.

To try the API in Postman, select the Postman icon at the top of any page, or <a href="/docs/openapi.json" download>download the spec</a>. In Postman, select **Import** and choose the file. The collection lists production and UAT; pick UAT to test.

## 2. Find out what you can send

Every integration starts here. `lead_schema` returns the fields your key can read and write, and which of them are required.

```bash title="Request"
curl "$BASE_URL/api/method/tatva_connect.api.partner.lead_schema" \
  -H 'Authorization: token <api_key>:<api_secret>'
```

The response has a `data` object with three parts:

- `fields`: the lead fields your key can use.
- `children`: the sections your key can use, such as lab results. You send each section as a JSON array inside the lead.
- `routing`: how your key sets the program and the product line and group of TatvaCare that your leads belong to. You don't send these yourself.

[Schema discovery](/discover-schema) walks through the full response.

## 3. Create your first lead

Use `lead_create` to create a lead. The CRM matches leads by phone number plus your key's product line and group. If the phone number already exists, the CRM updates that lead. So you can safely retry this call.

At minimum, send a phone number plus every field the schema marks as required.

The program field (`custom_current_program`) depends on your key's mode. `lead_schema` reports the mode in `routing.mode`:

| Mode | What you do |
|---|---|
| `list` | Send one of your allowed programs. If `routing.program_required` is `false`, you can leave it out and the CRM sets it later. |
| `forced` | Leave it out. Your key sets it, and the API ignores a program you send. |
| `none` | Leave it out. Leads have no program. |

In `list` mode, the API refuses a program that isn't on your allowed list. This example is for a `list` key. With a `forced` or `none` key, leave out `custom_current_program`.

```bash title="Request"
curl -X POST "$BASE_URL/api/method/tatva_connect.api.partner.lead_create" \
  -H 'Authorization: token <api_key>:<api_secret>' \
  -H 'Content-Type: application/json' \
  -d '{
    "mobile_no": "+919900000000",
    "first_name": "Asha",
    "last_name": "Rao",
    "custom_current_program": "<one-of-your-allowed-programs>"
  }'
```

The response has three top-level fields:

- `status`: `success` when the call worked.
- `action`: `created` for a new lead, or `updated` if the phone number was already known.
- `data`: the lead as saved, with every field your key can read. You don't need to read it back.

`data.name` is the lead's ID, for example `a7f3c9e12b`. Store it. You use it to read or update the lead later.

```json title="Response"
{
  "status": "success",
  "action": "created",
  "data": {
    "name": "a7f3c9e12b",
    "first_name": "Asha",
    "last_name": "Rao",
    "mobile_no": "+919900000000",
    "status": "New",
    "external_id": null,
    "source": "Source A",
    "custom_vertical": "Product Line A",
    "custom_group": "Group A",
    "custom_current_program": "Program A"
  }
}
```

The fields in this example are only a sample. Your key's own fields come from [`lead_schema`](/discover-schema).

Your key sets the product line and group for you. It also sets `source`, unless your key lets you send your own. You send only your lead data.

If the call fails, you get an error in one standard format. See [Errors](/partner-errors).

:::tip{title="Good practice"}

Build your integration in this order:

1. Call `lead_schema` when your integration starts, and build your requests from its response.
2. Send each lead with `lead_create`. It creates the lead or updates the existing one, and `action` tells you which.
3. Call `lead_get` first only when you need it. For example, to get a lead's `name` before you change one field, or to avoid overwriting data the CRM already holds.

Don't check with `lead_get` before every create. If two requests arrive at the same time, the lead can change between your read and your write. `lead_create` handles this for you. [Integration patterns](/integration-patterns) lists when a read first is the right choice.

:::

:::note{title="Moving a lead to a new program"}

To move a lead to a new program, send the same phone number with the new `custom_current_program`. The CRM updates the existing lead and keeps everything else. It never creates a second lead for the same phone number in the same product line and group.

:::

## 4. Read the lead back

```bash title="Request"
curl "$BASE_URL/api/method/tatva_connect.api.partner.lead_get?name=a7f3c9e12b" \
  -H 'Authorization: token <api_key>:<api_secret>'
```

The response contains the fields your key can read. Sections come back as arrays. They're empty here because you didn't send any. [Reading values](/responses#read-a-value-by-its-path) shows how to read a value from the response.
