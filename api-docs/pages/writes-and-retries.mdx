---
title: Writes and retries
description: "How to retry creates, updates, and deletes safely."
---

A request can time out after the CRM has already saved it. This page explains what happens when you send a write again, and how to retry without creating duplicates.

## Every record has a `name`

Every create returns the new record's unique ID in `data.name`. Store it against your own record. You use it for every later read, update, and delete.

A `name` is a string with no meaning. Don't parse it or build one yourself. In a bulk response, each record's `name` is at `results[i].data.name`. A [bulk job](/async-bulk) is the one exception: you address it by its `job_id`.

## What happens when you send a write again

| You send again | What happens |
|---|---|
| `lead_create` with the same phone number | The CRM updates the same lead. No duplicate. |
| Any other create: activity, call, note, file, ticket, or comment | The CRM creates a second record. |
| An update with the same values | The record ends up the same. No harm done. |
| A delete | The first one deletes the record. The second returns `404 not_found`. |

So creates are the risk. For every create except leads, a retry without protection makes a duplicate. [Lead identity](/concepts) explains why leads are different.

## `external_id` is only a label

`external_id` is an optional field for your own reference, such as your system's ID for the record. The CRM stores it and returns it on every read, so you can match records to your own.

The CRM never uses `external_id` to find a record or to spot a duplicate. Two records can have the same `external_id`. Once set, it can't be cleared. To find a record again, use its `name`.

## Make retries safe with `Idempotency-Key`

Send an `Idempotency-Key` header on a write. The first request with a key runs and the CRM stores its response. If you send the same request again with the same key, the API returns the stored response instead of running the write again.

```bash title="Request"
curl -X POST "$BASE_URL/api/method/tatva_connect.api.partner_activity.activity_create" \
  -H 'Authorization: token <api_key>:<api_secret>' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 5f2c1a9e-3b7d-4c8e-9f01-2a3b4c5d6e7f' \
  -d '{
    "lead": "a7f3c9e12b",
    "task_type": "Follow Up",
    "values": {}
  }'
```

Choose the key yourself. It must be:

- Unique to one write. Two different writes never share a key.
- The same on every retry of that write. A retry with a new key is a new write.

A random UUID per write works, if you store it until the write succeeds. A key made from your own record's ID needs no storage, because the same record always gives the same key. For example, a hash of `"activity:"` plus your activity ID.

The CRM keeps each key for at least 24 hours. Retries happen within minutes, so this is plenty. A key is for retrying one write, not for sending the same record again days later.

### What the key does

| Situation | Result |
|---|---|
| Same key, same body, first call succeeded | The API returns the first response again. Nothing new is saved. |
| Same key, first call still running | `409 conflict`. Wait, then retry with the same key. |
| Same key, different body or different endpoint | `422 conflict`. Use a new key. |
| Same key, first call failed | The failure isn't stored, so the call runs again. |
| No key | A retried create makes a second record. |

A returned response is a copy of the first one. So a retried create still says `"action": "created"`, with the same `name`. The same `name` proves that no second record was made.

A retried call still counts against your [rate limits](/rate-limits).

## When to retry

| The call ended with | What to do |
|---|---|
| A network error or a timeout | Retry with the same `Idempotency-Key`. |
| `429` or `503` | Wait `retry_after` seconds, then retry with the same key. See [Rate limits](/rate-limits). |
| `500` | Retry once with the same key. |
| `409 conflict` | Wait a moment, then retry with the same key. |
| Any other `4xx` | Don't retry unchanged. Fix the request first. See [Errors](/partner-errors). |

Retry with a growing wait, and add a small random delay. Stop after a few attempts and log the failure.

## Resending data in a daily sync

- Resending leads is safe. They update the same leads.
- Resending activities, calls, notes, files, tickets, or comments makes duplicates. Send only new records, and update existing ones by their `name`.

The safest way to sync is to send only what changed since your last sync.
