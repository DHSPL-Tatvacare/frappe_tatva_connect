The cross-cutting rules that apply to every call.

## Auth

Every request carries the key in one header:

```
Authorization: token <api_key>:<api_secret>
```

The literal lowercase `token`, one space, then `api_key:api_secret` joined by a colon. A missing or malformed header returns `401 unauthorized`. A key is verified with a single read:

```bash
curl -H 'Authorization: token <api_key>:<api_secret>' \
     "$BASE_URL/api/method/tatva_connect.api.partner.lead_schema"
```

A `200` with the schema confirms access. A key is requested from TatvaCare Ops.

## Phone format

Phone numbers use E.164: `+<country code><digits>`, no spaces or hyphens, for example `+919999000123`. Separators are removed and a bare 10-digit Indian number is completed to `+91…`, so `98765 43210` and `098765-43210` both store as `+919876543210`.

A number outside India **must** carry its own country code. Without a leading `+`, a number is read against India: `+966501234567` is stored as Saudi, while a bare `501234567` is refused and a bare `4155552671` is stored as Indian.

A number that is not a real number in any country is refused with `validation_error`. The full E.164 form is the safe default on every call.

## Idempotency and retry safety

| Call | Safe to retry |
|---|---|
| `lead_create` | Yes. Idempotent on phone, product line, and group. The same input converges to the same lead and never duplicates. |
| `lead_update` | Yes. The same payload produces the same final state, and children merge by key without clobbering. |
| `lead_delete` | Yes. A second delete of a removed lead returns `not_found`. |
| bulk variants | Yes. Each record is addressed by key, so a replay converges. Only the failed rows from `results[]` need re-sending. |
| reads (`lead_get`, `lead_list`, `lead_get_bulk`) | Yes, always. |

A retry after a network fault or a `5xx` is only safe if the request carried an `Idempotency-Key`. Without one, a create that timed out after the server committed will be duplicated by the retry. See [Writes and retries](/writes-and-retries).

## Partial updates never clobber

A write touches only the fields sent. Omitted top-level fields keep their values, and in child tables omitted fields and unmentioned rows are left alone. Incremental updates can be sent freely as new data arrives. See [Schema discovery](/discover-schema#child-tables).

## Versioning

This API is `v1`. Backward-compatible changes, such as new fields, new endpoints, new option values, or a new field granted to a key, ship without a version bump and do not break an integration. A breaking change, such as a field rename, an endpoint removal, or tighter validation, is announced by email to integration owners, with a migration window of at least four weeks.

Because the contract is whatever [`lead_schema`](/discover-schema) returns, code that reads the schema at runtime adapts to additive changes automatically.

## Environment

The API runs on two environments. A base URL is set for the target environment and used in every request. Examples in these docs use `$BASE_URL` in place of a fixed host.

| Environment | Base URL |
|---|---|
| Production | `https://one.tatvacare.in` |
| UAT (sandbox) | `https://one-uat.tatvacare.in` |

```bash
export BASE_URL=https://one.tatvacare.in
```

Each environment serves these docs at `/docs` on its own host, so the [API Reference](/partner-api) console addresses the environment it was opened on by default. A **Server** control on every operation switches it to the other; what that changes is described below.

For safe testing, clearly-test data is used, for example a `mobile_no` such as `+91999900xxxx`, which Ops removes periodically. A sandbox is requested from Ops.

## Browser clients and CORS

On every environment the docs are served at `/docs` on the same host that serves `/api`. The console's default server is therefore that same host, and a call to it needs no CORS setup.

Selecting the other environment in the **Server** control makes the call cross-origin. The browser then requires that environment to allow the docs origin, which Ops configures per site; where it has not been, the browser blocks the request and the console reports a network failure rather than an API error. Such a call also carries no cookie, so it is the key alone that is being tested.

:::warning{title="A signed-in CRM session answers same-origin calls"}

Because the console shares an origin with the API by default, a CRM session signed in to that host in the same browser is sent with every console request and answers it whenever the key header is absent or not well-formed. A key is therefore tested honestly in a private window, or after signing out of the CRM on that host. See [Authentication](/partner-validate-key).

:::

A partner web app hosted on a different origin should call the API from its own server, not the browser. This avoids CORS and keeps the key off the client. If a browser-to-API call from another origin is genuinely required, the origin is allowlisted by Ops.

## Support

Key requests, rate-limit increases, new-field grants, and integration issues are directed to TatvaCare Ops.

A report on a failing integration includes:

1. The exact request: URL, method, and body.
2. The full response: HTTP status and body.
3. The unique ID (`name`) of any affected lead.
4. Timestamps, with timezone.
