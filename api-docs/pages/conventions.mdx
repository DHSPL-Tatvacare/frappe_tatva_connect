These conventions apply to every call: environments, phone numbers, dates, versioning, calls from a browser, and how to get help.

## Environments

The API runs on two environments. Set `$BASE_URL` to the one you're calling. Every example in these docs uses it.

| Environment | Base URL |
|---|---|
| UAT (for testing) | `https://one-uat.tatvacare.in` |
| Production | `https://one.tatvacare.in` |

```bash title="Terminal"
export BASE_URL=https://one-uat.tatvacare.in
```

Build and test against UAT. Use test phone numbers there, such as `+91999900xxxx`, so test leads stand out. Each environment has its own keys.

## Authentication

Send your key in the `Authorization` header on every call:

```http title="Header"
Authorization: token <api_key>:<api_secret>
```

Use lowercase `token`, one space, then the key and the secret joined by a colon. [Authentication](/partner-validate-key) shows how to test a key.

## Phone format

Send phone numbers in E.164 format: `+`, the country code, then the number, with no spaces or hyphens. For example, `+919900000000`.

- The API removes spaces and hyphens.
- A number without a `+` is read as an Indian number.
- A number from another country must start with `+` and its country code.
- The API refuses a number that isn't valid in any country, with `400 validation_error`.

The full E.164 format always works, so send it every time.

## Dates and times

All dates and times are in India Standard Time (IST, UTC+05:30). This applies to the values you send, the values you read, and list filters such as `updated_after`.

| Kind | Format | Example |
|---|---|---|
| Date | `YYYY-MM-DD` | `2026-09-20` |
| Date and time | `YYYY-MM-DD HH:MM:SS` | `2026-09-20 10:30:00` |

Send times without a time zone offset. If your system stores times in UTC, convert them to IST before you send them.

A date without a time means 00:00 at the start of that day. So `created_before=2026-09-20` leaves out leads created later on 20 September. To include the whole day, send `2026-09-20 23:59:59`.

A filter date the API can't read returns `400 validation_error`, with the filter named in `error.fields`.

Every record returns `creation`, when it was created, and `modified`, when it last changed. A lead returns them when `lead_schema` lists them. A time the CRM sets itself, such as `modified`, can end in microseconds, for example `2026-09-24 11:05:12.483920`. Read the first 19 characters if you only need seconds.

## Versioning

This API is version 1. Changes that don't break an integration ship without a new version. For example: new fields, new endpoints, new values, or a new field granted to your key.

A breaking change is announced in the [Changelog](/changelog). For example: a renamed field, a removed endpoint, or a stricter check.

If you build your requests from [`lead_schema`](/discover-schema) at runtime, your integration picks up new fields without a code change.

## Calls from a browser

Call the API from your own server, not from a web browser. This keeps your key out of the browser. It also avoids cross-origin (CORS) errors.

The playground in the [API Reference](/partner-api) calls the environment it's opened on. It has a **Server** control to switch to the other environment. A call to the other environment is cross-origin. If that environment doesn't allow it, the browser blocks the call and the playground shows a network error, not an API error.

If your web app must call the API from a browser, ask TatvaCare to allow your web app's address.

## Support

Contact TatvaCare for new keys, higher rate limits, new fields, and help with a failing integration.

When you report a problem, include:

1. The request: URL, method, and body. Remove your key and secret first.
2. The response: HTTP status and body.
3. The `name` of any record involved.
4. The time of the call, with its time zone.
