title: Rate limits
---

A key has three independent budgets. Each is configured per key, and any of them can be raised on request.

| Budget | Default | Counts |
|---|---|---|
| Request rate | 120 requests per minute | every call, read or write |
| **Bulk rate** | **one bulk call per 5 seconds, one in flight at a time** | bulk write calls only |
| Daily record volume | 10,000 records read and 10,000 records written per day | rows touched, not calls |

Each budget is enforced twice: **per key**, and again **at platform level** across every key on the platform. A call is refused if either is exhausted, so a key can be throttled while still inside its own budget. The per-key numbers above are what an integration is sized against; the platform ceiling protects the service.

When any budget is exceeded, the next call returns **HTTP 429** with this body:

```json
{
  "status": "error",
  "error": {
    "code": "rate_limited",
    "message": "Bulk rate limit exceeded. Retry in 5s.",
    "retry_after": 5
  }
}
```

`error.retry_after` gives the number of seconds to wait before the next retry. This value is used directly, not guessed.

## The bulk budget is separate, and deliberately tight

A bulk write is not the same animal as a lead read. It holds every record's row locks for the length of its transaction, so what has to be limited is not how many bulk calls arrive per minute, but **how many are allowed to run at the same time**. That number is **one**.

A second bulk call sent while the first is still running is refused with a 429 before it reaches the database. Two bulk writes are therefore never in flight together, and the write conflicts that concurrency would otherwise cause do not arise.

The practical rule is simple:

> **Bulk calls are sent one at a time, in sequence, never in parallel.**

Single-record calls are unaffected. They may be sent concurrently, up to the request rate.

The bulk budget is enforced **at platform level**, not per key. While one integration runs a large
backfill, another integration's bulk call waits its turn and is told how long to wait. This is
deliberate: the constraint being protected is a single database index that every key writes through,
so a per-key limit alone would not protect it. A backfill that must not be delayed by another one is
scheduled with Ops.

## Bulk still saves the request budget

A bulk call of up to **25 records** counts as **one** request against the request budget. Each record still counts against the daily volume budget. So a batch of 25 leads costs one request, not 25.

**Files are the exception: up to 5 per call.** A file is not a row. Each one is decoded, scanned for malware and written to storage, which takes roughly a second, so twenty-five of them would be a request no gateway waits for. Every `*_schema` endpoint publishes the ceiling that applies to it in `bulk.max_per_call`, and that is the number the API enforces — it is read rather than assumed.

At one bulk call every 5 seconds, that is 300 records a minute — comfortably more than the daily volume budget allows in an hour, so the volume budget, not the bulk rate, is what a real integration runs into first.

## Response headers

Every response reports the current state of the request budget, so a client can slow down before a 429 is reached:

| Header | Meaning |
|---|---|
| `RateLimit-Limit` | the request budget for the window |
| `RateLimit-Remaining` | requests left in the current window |
| `RateLimit-Reset` | seconds until the window resets |
| `Retry-After` | on a 429 or 503 only, seconds to wait before retrying |

## Retry handling

Two statuses are retried, and both are safe to retry:

| Status | `error.code` | Meaning |
|---|---|---|
| **429** | `rate_limited` | A budget is exhausted. The call was refused *before* the write ran, so nothing was saved. |
| **503** | `write_conflict` | A concurrent write conflicted with the batch and the database rolled it back. **Nothing was saved** — not even the records that had already succeeded inside the call. |

Both carry `error.retry_after`. Both mean the request never took effect, so retrying is safe with or without an `Idempotency-Key`. Any *other* failed write is only replay-safe if it carried one — see [Writes, addressing and retries](/writes-and-retries).

```python title="Python"
import time

RETRYABLE = (429, 503)   # rate_limited, write_conflict — neither ever saved anything

def call_with_retry(do_request, max_attempts=6):
    for attempt in range(max_attempts):
        r = do_request()
        if r.status_code not in RETRYABLE:
            return r
        body = r.json()
        wait = body.get("error", {}).get("retry_after") or (2 ** attempt)
        time.sleep(wait)
    return r
```

```javascript title="Node"
const RETRYABLE = [429, 503];   // rate_limited, write_conflict — neither ever saved anything

async function callWithRetry(doRequest, maxAttempts = 6) {
  let res;
  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    res = await doRequest();
    if (!RETRYABLE.includes(res.status)) return res;
    const body = await res.clone().json();
    const wait = body?.error?.retry_after ?? 2 ** attempt;
    await new Promise((r) => setTimeout(r, wait * 1000));
  }
  return res;
}
```

## Spending the budget wisely

- **Use bulk calls, one at a time.** Up to 25 records — or 5 files — are sent in one request, which spends only one unit of the request budget. The exact ceiling is read from `bulk.max_per_call` in the entity's schema. Sending calls in parallel does not go faster; it is refused.
- **Slow down large backfills.** The daily volume budget, not the request rate, is the real ceiling on a backfill. A load larger than the daily budget is planned with Ops rather than attempted in one run.
- **Cache repeated reads.** When the same lead is read again and again, the stored response is reused instead of fetched each time.

:::note{title="Raising a budget"}

A sustained integration that needs more than the defaults contacts TatvaCare Ops. All three budgets are set per key and can be raised.

:::
