This page lists the default rate limits, what happens when you reach one, and how to retry.

## The limits

These are the default limits for each key. TatvaCare can raise them on request.

| Limit | Default |
|---|---|
| Calls | 120 a minute |
| Bulk calls | 1 every 5 seconds |
| Records read | 10,000 in any 24 hours |
| Records written | 10,000 in any 24 hours |
| Records in one bulk call | 25, or 5 for `file_attach_bulk` |
| Records in one list page | 200 |

A bulk call counts as one call against the call limit, however many records it carries. Its records still count against the daily record limits. A list counts the records it returns.

Bulk reads, such as `lead_get_bulk`, count as bulk calls too. So does reading [bulk job](/async-bulk) results.

[Bulk jobs](/async-bulk#limits) have their own, larger limits.

## How the limits work

The API measures each limit with a token bucket:

- Each call uses one token. For record limits, each record uses one token.
- Tokens refill steadily at the limit's rate: for calls, 2 every second.
- When no tokens are left, the API refuses the call until enough tokens refill.

Tokens refill continuously, not all at once at the start of each minute.

Send your calls at a steady pace, below your limit. Spread large loads over time, or use [bulk calls](/leads#bulk) and [bulk jobs](/async-bulk). If you send faster than your limit, the API refuses calls, and `retry_after` tells you how long until enough tokens refill.

## When you reach a limit

The API refuses the call before it runs, so nothing was saved. The response tells you how long to wait:

```json title="Response"
{
  "status": "error",
  "error": {
    "code": "rate_limited",
    "message": "Rate limit exceeded. Retry in 12s.",
    "retry_after": 12
  }
}
```

| Status | Code | Meaning |
|---|---|---|
| `429` | `rate_limited` | Your key reached one of its limits. |
| `503` | `server_busy` | The service as a whole is busy. This can happen even when your key is under its limits. |

When the API refuses a call for a limit, the response carries `error.retry_after`, the number of seconds to wait, and a `Retry-After` header with the same value.

## Response headers

When limits apply to your key, each response carries headers about your call limit:

| Header | What it tells you |
|---|---|
| `X-RateLimit-Limit` | Your calls per minute. |
| `X-RateLimit-Remaining` | How many calls you can make right now, shown up to your per-minute limit. |
| `X-RateLimit-Reset` | Seconds until your bucket refills to your per-minute limit. |

These headers describe the call limit only. They don't show the bulk or daily record limits.

## Retry

When you get `429` or `503`:

1. Wait for `error.retry_after` seconds. Add a small random delay, so many clients don't retry at the same moment.
2. Send the same call again. For a write, send the same `Idempotency-Key`. See [Writes and retries](/writes-and-retries).
3. If the call fails again, wait longer each time.

A `503 server_busy` doesn't always carry `retry_after`. For example, it doesn't when the service is briefly overloaded. Then wait a few seconds, and double the wait after each retry.

Another `503`, `write_conflict`, means a bulk call collided with other work and nothing was saved. Retry it the same way.

## Use your limits well

- Send bulk calls one after another, not in parallel. A second bulk call within 5 seconds returns `429`.
- Send only the records that changed. The daily limits count records, so resending unchanged records uses them up.
- Read the schema once when your integration starts, not before every call.
- Page lists with `limit=200`, the largest page, to make fewer calls.
- For thousands of records, use a [bulk job](/async-bulk).
