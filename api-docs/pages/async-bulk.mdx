title: Async bulk jobs
description: "Load large batches of leads or activities as background jobs."
---

A bulk job loads thousands of records in the background. You submit the records once, check the job until it finishes, and then read the result of each record. Use a job for backfills and large loads. For up to 25 records, the bulk calls on each resource page are simpler, because the results come back in the same call.

## Operations

All job endpoints start with `$BASE_URL/api/method/tatva_connect.api.partner_bulk_job.`

| Operation | Method | Endpoint | What it does |
|---|---|---|---|
| Submit | `POST` | `create` | Submits a job and returns its `job_id`. |
| Check | `GET` | `get` | Reads a job's status and counts. |
| Results | `GET` | `results` | Reads the result of each record, a page at a time. |
| Cancel | `POST` | `cancel` | Stops a job. |

A job can run one of two operations:

| `operation` | Does the same as |
|---|---|
| `lead_create` | [`lead_create`](/leads#create), once per record |
| `activity_create` | [`activity_create`](/activities#create), once per record |

## Submit a job

Send the records in the body with `"format": "inline"`:

```bash title="Request"
curl -X POST "$BASE_URL/api/method/tatva_connect.api.partner_bulk_job.create" \
  -H 'Authorization: token <api_key>:<api_secret>' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: <a-new-uuid-per-job>' \
  -d '{
    "operation": "lead_create",
    "format": "inline",
    "records": [
      { "mobile_no": "+919900000000", "first_name": "Asha", "last_name": "Rao" },
      { "first_name": "Kiran" }
    ]
  }'
```

```json title="Response"
{
  "status": "success",
  "action": "created",
  "data": {
    "job_id": "j5r8t2w6yq",
    "status": "UploadComplete"
  }
}
```

The API returns `202`. That means it accepted the job, not that the job is done. Store the `job_id`. You need it for every other job call.

To send the records as a file instead, set `format` and send the file:

| `format` | The file holds | Works for |
|---|---|---|
| `jsonl` | One JSON record per line | Leads and activities |
| `csv` | A header row, then one record per row | Leads only |
| `xlsx` | A spreadsheet read the same way as CSV | Leads, with flat fields only |

Send the file as a multipart file upload, or as base64 in `content_base64`. To use an `Idempotency-Key` with a file, send it as `content_base64`. A multipart upload with an `Idempotency-Key` returns `400`.

This example submits a JSONL file as base64:

```bash title="Request"
curl -X POST "$BASE_URL/api/method/tatva_connect.api.partner_bulk_job.create" \
  -H 'Authorization: token <api_key>:<api_secret>' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: <a-new-uuid-per-job>' \
  -d '{
    "operation": "lead_create",
    "format": "jsonl",
    "content_base64": "<base64-of-the-file>"
  }'
```

In CSV and XLSX files, the header row names the fields. The API skips blank rows. A row with the wrong number of columns fails on its own, and the other rows still load. For activities, and for leads with sections, use inline records or JSONL.

## Check a job

```bash title="Request"
curl "$BASE_URL/api/method/tatva_connect.api.partner_bulk_job.get?job_id=j5r8t2w6yq" \
  -H 'Authorization: token <api_key>:<api_secret>'
```

```json title="Response"
{
  "status": "success",
  "action": "fetched",
  "data": {
    "name": "j5r8t2w6yq",
    "partner": "api@partner.example.com",
    "status": "InProgress",
    "operation": "lead_create",
    "total": 2,
    "processed": 1,
    "succeeded": 1,
    "failed": 0,
    "error_summary": null,
    "submitted_at": "2026-09-26 09:00:04.518302",
    "started_at": "2026-09-26 09:00:05.002117",
    "finished_at": null
  }
}
```

The counts go up as the job runs. For a file job, `total` is `0` until the job has read the file.

A job moves through these statuses:

<Mermaid chart={`
stateDiagram-v2
    [*] --> UploadComplete
    UploadComplete --> InProgress: job starts
    InProgress --> JobComplete: every record handled
    InProgress --> Failed: job stopped
    UploadComplete --> Aborted: cancel
    InProgress --> Aborted: cancel
    JobComplete --> [*]
    Failed --> [*]
    Aborted --> [*]
`} />

| Status | Meaning |
|---|---|
| `UploadComplete` | The job is waiting to start. |
| `InProgress` | The job is running. |
| `JobComplete` | Every record was handled. Some records can still have failed. Read the results. |
| `Failed` | The job stopped before the end. `error_summary` says why. |
| `Aborted` | The job was cancelled. |

A job fails when the file has more than 50,000 records, when your key's daily job limit runs out, or when it runs for more than an hour. Records handled before a failure stay saved. You can't restart a finished job. Submit a new one for the records that are left.

Check a job every few seconds, not in a tight loop. TatvaCare can also set up a webhook that calls your server when a job finishes. Ask TatvaCare if you need one.

## Quiet and live jobs

Each key runs its jobs in one of two modes. TatvaCare sets the mode on your key, and you can't change it per job.

| Mode | What the CRM does with each record |
|---|---|
| Quiet | Saves it and runs data checks, such as the duplicate check. It doesn't run follow-up work, such as assigning leads to people, sending notifications, or running automations. |
| Live | Treats it like a record sent with a direct call, including all follow-up work. |

Quiet is the default. It suits backfills of past records, where follow-up work would be wrong or noisy. Ask TatvaCare which mode your key uses. Direct calls, including bulk calls, are never quiet.

## Read the results

```bash title="Request"
curl "$BASE_URL/api/method/tatva_connect.api.partner_bulk_job.results?job_id=j5r8t2w6yq&limit=200" \
  -H 'Authorization: token <api_key>:<api_secret>'
```

```json title="Response"
{
  "status": "success",
  "action": "fetched",
  "data": {
    "total": 2,
    "count": 2,
    "offset": 0,
    "limit": 200,
    "has_more": false,
    "results": [
      { "record_index": 0, "action": "merged", "record_name": "a7f3c9e12b", "error_code": null, "error_message": null, "error_fields": null, "error_detail": null },
      { "record_index": 1, "action": "failed", "record_name": null, "error_code": "validation_error", "error_message": "A lead is identified by its phone number and this record carries none. Send `mobile_no` in E.164 (for example +919876543210).", "error_fields": ["mobile_no"], "error_detail": null }
    ]
  }
}
```

Each row is the result of one record. `record_index` is the record's position in what you sent, starting at `0`. `action` is one of:

| `action` | Meaning |
|---|---|
| `created` | A new record was created. `record_name` is its `name`. |
| `merged` | A lead with this phone number already existed, so the job updated it. |
| `failed` | The record wasn't saved. `error_code` and `error_message` say why. |

These rows are flat. They don't have the `data` and `error` objects of a [bulk call response](/responses#a-bulk-call). Read `record_name` and `error_code` directly.

`results` counts as a bulk call, so by default you can call it once every 5 seconds. Use `limit=200`, the largest page, to read results in as few calls as possible.

## Retry failed records

A finished job doesn't retry. To retry, collect the failed rows, fix the records, and submit them as a new job.

To make a submit safe to retry, send an `Idempotency-Key`. If you send the same key and the same body again, the API returns the first response instead of creating a second job. See [Writes and retries](/writes-and-retries).

## Cancel a job

```bash title="Request"
curl -X POST "$BASE_URL/api/method/tatva_connect.api.partner_bulk_job.cancel" \
  -H 'Authorization: token <api_key>:<api_secret>' \
  -H 'Content-Type: application/json' \
  -d '{ "job_id": "j5r8t2w6yq" }'
```

- A job that hasn't started becomes `Aborted` at once. Nothing was saved.
- A running job stops after its current batch of records. The response still shows `InProgress`. Check the job until it shows `Aborted`.
- When a job is cancelled, the CRM deletes the records it created. Leads it only updated stay updated.
- If some created records can't be deleted, the job still ends `Aborted`, and `error_summary` tells you how many are left.
- Cancelling a job that has finished returns `409 conflict`.

## Limits

These are the default limits. TatvaCare can raise them on request.

| Limit | Default |
|---|---|
| Records in one inline job | 10,000 |
| Records in one file | 50,000 |
| File size | 50 MB |
| Jobs running at the same time, per key | 5 |
| Records written by jobs, per key, per day | 1,000,000 |

Job records don't count against the 10,000 records a day that direct calls can write. If you already have 5 jobs running, a new submit returns `429 rate_limited`. If the service has too many jobs queued, a submit returns `503 server_busy`. In both cases, wait for `retry_after` seconds and submit again.

## Keeping results

A job and its results are kept for seven days after the job finishes. Read and store the results you need before then.

## Errors

| Status | Code | When |
|---|---|---|
| `400` | `validation_error` | `operation` or `format` isn't valid. `records` is empty or has more than 10,000 records. The file is missing, too large, or not valid base64. CSV was sent for `activity_create`. A multipart file was sent with an `Idempotency-Key`. |
| `404` | `not_found` | The job doesn't exist, or it belongs to another key. |
| `409` | `conflict` | The job has already finished, so it can't be cancelled. Or an `Idempotency-Key` is still in use. |
| `422` | `conflict` | An `Idempotency-Key` was used before with a different body. |
| `429` | `rate_limited` | Your key already has 5 jobs running, or you called `results` too soon. |
| `503` | `server_busy` | The service has too many jobs queued. |

[Errors](/partner-errors) explains the error format.
